MegaPlay stopped returning a stream

Why episodes 10 and 12 would not play, what actually fixed it, and how to keep a scraper working when a host changes its extraction contract.

6 September 2026 · anikototv.to → megaplay.buzz
Shipped OTA to runtime 14603ec1 (v1.1.0)

Summary

MegaPlay changed /stream/getSources to return an encrypted blob in place of the stream URL. Tsuzuku read the old field, got nothing, and reported "no available servers" on any episode whose only servers were MegaPlay-backed.

What actually fixed it

Not decryption. MegaPlay's own web client had already moved to a second endpoint, /stream/getSourcesNew, which still returns the file in plaintext. Asking for that first restored playback without decrypting anything.

The decryption exists as a fallback for the day that endpoint disappears. It does not run during normal playback.

The symptom

Episodes 1–9 and 11 of a twelve-episode series played. Episodes 10 and 12 said no servers were available — while the same episodes played fine in a browser on the site itself.

That split is the most useful thing in the whole incident, because it rules out the obvious explanations. It is not the network, not DNS, not an ISP block, and not the site being down: those would take out the whole series, not two episodes of it.

The chain

The video never comes from the site you browse. Four hops sit between a tap and a picture, and each one can fail independently:

anikototv.to /ajax/server/list → which servers exist for this episode anikototv.to /ajax/server?get=id → a link id becomes an embed URL megaplay.buzz /stream/<path> → the embed page, carrying a numeric data-id megaplay.buzz /stream/getSources → the data-id becomes a stream URL <cdn host> master.m3u8 → the playlist, then segments

Diagnosing this means walking the hops in order and finding the first that misbehaves. Checking the site in a browser tests hop one, which was never the problem.

Root cause

Hop four changed shape. It used to answer:

{ "sources": { "file": "https://…/master.m3u8" }, "tracks": [ … ] }

It now answers:

{ "tracks": [ … ], "t": 1, "intro": {…}, "outro": {…},
  "server": 4, "enc": "wdeBruh3qqn_i5wUNnyaPQQl1wp7r0Sr…" }

sources is gone entirely, replaced by enc. The extractor read j.sources.file, got null, and returned an empty source list. An empty list is indistinguishable from "this server has nothing", so it surfaced as a missing server rather than a changed format.

Why only some episodes broke

The site lists three server names per episode, but they are not three sources:

LabelResolves toBackend
Vidstream-2megaplay.buzz/stream/s-2/<id>/subserver: 4
HD-1the same URL with ?s=tcdnserver: 4 — same stream
VidPlay-1vidtube.site/stream/…server: 6 — genuinely separate

Vidstream and HD are one stream listed twice; both embeds return the same data-id. Only VidPlay is a different chain, and it never stopped returning plaintext.

So every episode that still played was quietly running on VidPlay. Episodes 10 and 12 simply were not listed with a VidPlay entry, leaving them with two links onto the one broken backend.

Generalisable

When a failure splits along an axis that looks arbitrary, enumerate what each case actually resolves to rather than trusting the labels. Three server names hiding two backends is why "try another server" appeared to work for some episodes and not others.

The fix: a second endpoint

MegaPlay's own player kept working throughout, which means it was getting a URL somehow. It was calling a different endpoint:

EndpointReturns
/stream/getSourcessources: null plus enc
/stream/getSourcesNewsources.file in plaintext, no enc

The fix is to ask for the new endpoint first and keep the old one as a fallback:

async function getSources(base, embed, id) {
    const headers = { 'User-Agent': UA, Referer: embed,
                      'X-Requested-With': 'XMLHttpRequest' };
    try {
        const rNew = await hostFetch(`${base}/stream/getSourcesNew?id=${id}`, { headers });
        const jNew = JSON.parse(rNew.body || 'null');
        if (jNew && (jNew.sources || jNew.enc)) return jNew;
    } catch { /* fall through */ }

    const r = await hostFetch(`${base}/stream/getSources?id=${id}`, { headers });
    try { return JSON.parse(r.body || 'null'); } catch { return null; }
}

The guard matters: a 404 body fails JSON.parse and falls through cleanly, and a response with neither field is treated as no answer rather than a valid empty one.

This is safe for other hosts. VidPlay's getSourcesNew returns byte-identical content to its getSources — same file, same tracks — so it returns on the first call and costs no extra round trip.

The CDN trap

Getting a URL back is not the same as getting a playable one. The decrypted legacy payload points at a host that refuses video:

HostVideo master.m3u8Subtitle .vtt
cdn.imgnex.top403200
ncdn.imgnex.top200200

Video is blocked on the bare host while subtitles still serve, so the rewrite is video-only:

const file = rawFile.replace(/^https?:\/\/cdn\.imgnex\.top\//i,
                             'https://ncdn.imgnex.top/');

Rewriting subtitle URLs too would be harmless here but wrong in principle — they are not blocked, and the narrower rule is the one that stays correct when only one of the two changes.

Worth knowing

getSourcesNew returns a different host again (megap.shiora.site), so on the working path this rewrite never fires. It only matters on the fallback.

A failure mode worth naming: the load-time crash

The first decryption module bundled a crypto library still wrapped in a UMD header — the pattern that probes for a global object to attach itself to, ending in })(_root) or })(this).

Under Hermes, and under any ES-module transpile, top-level this is undefined. Reaching for a property on it throws while the module is being imported, which means:

  • the failure happens before any exported function can run;
  • every importer of that module fails with it;
  • and the visible symptom is not "decryption failed" but "decryption never happened".
Diagnostic consequence

A module that throws at import time produces the same silence as a module that was never called. If a diagnostic cannot tell those apart, it will send you looking in the wrong half of the chain — which is exactly what happened here.

The fix is to not carry UMD wrappers into a bundler-managed module at all. A focused implementation of just the primitive needed — one cipher, one mode, one padding scheme — has no global scope to reach for and nothing to fail on load.

The decryption, as an interface

The cipher is AES-256-CBC with static parameters and PKCS#7 padding, over a Base64URL payload. The ciphertext is a clean multiple of 16 bytes with no salt header, so it is raw CBC rather than the OpenSSL Salted__ framing that most libraries assume by default — which is why a naive drop-in call fails before the key is ever consulted.

The parameters themselves live in api/megaplay.ts and are not reproduced here. What matters for integration is the contract:

export interface DecryptedSources { file: string; }

export type DecryptErrorReason =
    | 'invalid_input'      | 'bad_base64'
    | 'bad_ciphertext_length' | 'decryption_failed'
    | 'bad_pkcs7_padding'  | 'json_parse_error'
    | 'no_file_in_payload';

/** Never throws. Returns null and records why. */
export function decryptSources(enc: string): DecryptedSources | null;
export function decryptSourcesWithDiagnostic(enc: string): DecryptDiagnostic;
export let lastMegaPlayError: DecryptErrorReason | null;

Two properties that make it safe to integrate

  • It never throws. Extraction runs inside a fallback loop that moves to the next server on an empty result. A throw would escape that loop and abort the whole resolve, turning one bad server into a dead episode.
  • It resets its error flag on entry. decryptSourcesWithDiagnostic clears lastMegaPlayError before doing anything, and decryptSources delegates to it. Without that reset, reading the flag after a later call would report a stale reason from an earlier server.

Wiring it into an extractor

One line, and the ordering in it is the whole design:

const rawFile = j?.sources?.file
    ?? j?.sources?.[0]?.file
    ?? (typeof j?.enc === 'string' ? decryptSources(j.enc)?.file ?? null : null);
if (!rawFile) return [];

Plaintext is tried first, deliberately:

  • hosts that never changed keep their existing path and cost nothing;
  • the decrypt runs only where it is actually needed;
  • and if a host reverts to plaintext, it starts working again with no code change.

Everything downstream — splitting the master playlist into a quality ladder, subtitle tracks, hardsub flags, subtitle/video pack skew — keys off the resulting file and needs no knowledge that a decrypt happened.

Reading a live binding

lastMegaPlayError is reassigned, so import the module namespace (import * as megaplay) and read megaplay.lastMegaPlayError rather than destructuring it. A named import of a mutable binding can be snapshotted by a bundler, and the failure mode is silent: the flag reads null forever and every decrypt failure is misreported as an empty server.

Making the diagnostic tell the truth

Two things went wrong with diagnostics during this incident, both instructive.

Identical messages for different causes

An empty source list has two very different causes — the server had nothing, or the decrypt failed on what it had — and they want opposite fixes. A rotated key is not a dead server. Separating them:

const emptyReason = (fallback) => (megaplay.lastMegaPlayError
    ? `Decrypt failed — ${megaplay.lastMegaPlayError.replace(/_/g, ' ')}`
    : fallback);
The mistake worth avoiding

The first version of that fallback string was byte-identical to the message it replaced. That made an old build and a new build print the same text, so the diagnostic could not even establish which code was running. Give a replacement message different wording, or it cannot do the one job it was added for.

Stopping at the first success

The test originally returned as soon as one server answered. That tells you playback works today and nothing about whether the rest of the chain still would — and since the decrypt fallback is never reached while getSourcesNew answers, it was never exercised at all.

A fallback nobody has run is a guess. The test now probes every server, and adds a step that asks the legacy endpoint for an encrypted payload on purpose and puts it through the decrypt. That result is reported beside the overall verdict rather than folded into it: the fallback being broken is worth seeing, but it does not mean the video is unwatchable today.

Operational notes

  • The decrypt is dormant. While getSourcesNew answers, decryptSources never executes in normal playback. A green connection test confirms the endpoint works; only the explicit decrypt step covers the fallback.
  • Static keys rotate. When they do, the fallback fails while playback continues on the plain endpoint — a silent degradation. The decrypt step in the connection test is what surfaces it.
  • Both paths can go at once. If getSourcesNew is retired and the key rotates in the same change, there is no working path. Worth checking the endpoint occasionally rather than assuming.
  • Host names are never hardcoded. CDN hostnames come out of the response; only the embed host patterns are matched, and loosely. A CDN migration should need no code change — the ncdn rewrite is a deliberate exception to that rule and should be revisited if the block lifts.

Method, generalised

What made this tractable was not knowing anything about the cipher. It was:

  1. Reproduce the exact chain outside the app. Curl each hop in order with the same headers. The app adds caching, retries and racing that hide which hop actually failed.
  2. Find the discriminator. Something worked and something did not. Enumerate what each case resolves to until the difference is concrete — here, the presence of a VidPlay entry.
  3. Compare against the working client. The site's own player kept playing, so it was doing something different. That difference was the fix, and it was cheaper than the cryptography.
  4. Verify to the bytes. A well-formed manifest is not a playing video. Fetch a segment and check it is media, not an error page — a playlist can return 200 and contain nothing but dead URLs.
The cheapest fix is usually not the clever one

Considerable effort went into the encryption before anyone checked whether the site had simply moved endpoints. It had. Look for the path the working client takes before reverse-engineering the one it abandoned.
